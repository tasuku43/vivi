判断の根拠と、次に検証すること

A · 静かな読書面

実画面の1280px幅では、左280px・右396pxが使われ、中央は604px。5個のタブ管理ボタンが1枚目の文書名まで押し縮めていた。管理操作をメニューに集約し、左右の初期幅を210px / 310pxとして比較する。

最も小さい変更で読む面積が増える。タブ一括操作は1手増える。既存のリサイズ値は尊重し、長い同名タブ・分割表示・キーボード操作をFacadeで確認する。

B · 文脈のある指摘

現在の入力見出しは「Line 5 / Composing」。読者が見ている節と引用を先に見せ、ソース行を補助情報へ。本文の再配置を起こさない既存のポップオーバー方針を維持する。

初回の指摘が分かりやすい。引用は場所を使うため長さを制限する。Markdown / HTML・文書更新・Escapeでの退避・再開時のフォーカスを確認する。

C · 明確な受け渡し

公開前に「どの文書の何件か」「入力中は含まれない」を一か所で示す。Published / Unseen / Seenの意味を短文で説明し、受信箱や完了管理を追加しない。

複数文書の指摘をまとめるときに有効。常時表示では右側が重くなるため、公開対象があるときに限定する。全体 / 現在文書 / 行単位の対象件数を検証する。

推奨：Aを最初の縦断スライスとし、Bの入口とCの公開説明を段階的に足す。既存の注意ウィンドウやコメントの状態遷移は維持する。
