ファイルの場所と、文書の意味。
ツリーは、どちらを先に伝える？

同じパス・同じ並び・同じ選択で4案を比較。H1を伝える方向は文書中心のViviに合う。ただしH1は変わり、重複し、存在しないこともある。

まずの推奨は B：ファイル名を残し、H1を添える。既存の空間的な記憶を守りながら内容が分かる。Cは文書名で探す人向けの有力案。Aの完全置換は比較用、Dは密度を優先する場合の選択肢。

行をクリックすると4案の選択が連動します。Dはポインターを重ねる／Tabで行にフォーカスすると、下部にH1が出ます。フォルダーは開閉可能。幅が足りない場合は比較欄を横にスクロールできます。

H1の表示は筋がよい。H1への完全置換は弱い。

README.mdや番号付きファイルは、ファイル名だけでは意味が薄い。H1は「何が書かれているか」を伝える。その一方、「要件一覧」のようなH1は重複する。エージェントがH1を書き換えた瞬間に、見覚えのあるラベルが消えるのも置換案の弱点。

過去の文書モデルは表示タイトルを重視する一方、ツリーについては「file and directory labels come from their real names」と明記している。Bはそのまま沿える。Cはファイル名を保持したうえで、ラベルの優先順位を意図的に変える判断になる。

ツリーの中にH1を子ノードとして置く？

推奨しない。同じ文書への入口が親と子に二重化し、フォルダー展開と文書内アウトラインが混ざる。H1はファイルの説明として持ち、H2への移動はDocumentのアウトラインに任せる方が一貫する。

幅と密度も、選択の一部

B/Cは全行を固定の2段にする。選択時にだけ行を高くすると周囲の行が動くため採用しない。210pxでは、深い階層に入るほどH1が切れる。280pxで意味が読めるかをまず見てほしい。340pxは読みやすいが、本文の幅を使う。

Dは一行の密度を維持する。H1表示枠は常設し、ホバーやフォーカスで高さを変えない。既知のファイルを素早く開く人にはよいが、文書群を意味で眺める体験は弱い。

次の実装で守る境界

ファイルの識別子と順序はパスを基準に維持する。H1を得るために各ツリー行から本文を読み込まない。既存のツリーDTOにタイトルはないため、タイトル抽出・キャッシュ・更新通知は別の設計が必要。初回取得前にもファイルはすぐ開けることが前提。

例外でも、嘘をつかない表示

状態 このモックの扱い 設計上の意味
H1なし ファイル名を表示。副行や詳細に「H1なし」。 ファイル名を消さない。勝手なタイトルを生成しない。
H1が未取得 ファイル名＋「見出しを取得中」。 H1なしと区別。文字が取れるまで操作を待たせない。
同じH1 同じフォルダーの01-requirements.mdと02-requirements.md。 Aでは見分けにくい。B/Cは実ファイル名を見て選べる。
H1が長い 行内では1行で省略。選択詳細・Dの枠・ツールチップで補う。 行の高さを揃える。アクセシビリティ名には省略しないH1とパス。
H1が更新された 選択と並びは維持。更新ドットだけを添える。 別ファイルになったように振る舞わない。
HTML 文書本文の最初のH1を比較用に使用。 ブラウザーのtitle要素とH1は別物。優先順位は未決定のため、黙って混ぜない。
