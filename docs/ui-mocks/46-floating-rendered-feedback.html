Concept 46 · rendered feedback parity

Comments float. Documents stay put.

Markdown and HTML should share one rendered-feedback model: the selected block is highlighted in place, while the composer lives in a viewer-level overlay that never becomes part of the authored document layout.

Selected: Concept B — one anchored rendered composer Markdown and HTML share one no-reflow popover that stays beside the target so the commented content remains readable.
Selected

A · Fixed stage

Markdown uses the same single, fixed right-middle composer as HTML. The anchor highlight carries location; the card position stays stable.

Wins when

Consistency and zero layout shift matter most. Long tables, lists, code blocks, and Mermaid output never move.

Tradeoff

Only one rendered composer is expanded at a time. Other unsaved inputs remain recoverable but collapsed.

B · Anchor popover

The card floats near the selected block and follows it while scrolling. It remains outside document flow but keeps stronger spatial proximity.

Wins when

Reviewers frequently compare the input with a small nearby paragraph and the viewport has enough free space.

Tradeoff

Placement adapts around tables and screen edges, so the card may move from beside the target to above or below it. Markdown and HTML use the same collision rule and never cover the selected content.

C · Comment rail

A persistent viewer-side rail holds the composer while the selected Markdown block remains highlighted in the document.

Wins when

Several threads need to stay visible and the reviewer accepts a more tool-like, less document-native surface.

Tradeoff

The rail covers more content on narrow viewers and diverges furthest from the current HTML interaction.

Shared queue policy

Missing source is not an active file

Once a path is known missing—either from the loaded tree or a failed file read—it leaves active counts and Next queued immediately. Feedback data remains recoverable in one collapsed, non-actionable section.
